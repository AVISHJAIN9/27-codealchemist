# 14.17 Classic System Design Interview Scenarios Applied to TruthGuard

This chapter applies standard system design interview questions directly to TruthGuard’s cyber-defense domain, demonstrating how the platform's architectural building blocks scale to enterprise workloads.

## 1. Design TruthGuard at 100x Scale

```mermaid
flowchart TD
    GlobalUsers[100,000 Analysts] --> Cloudflare[Cloudflare Anycast DNS & DDoS Shield]
    Cloudflare --> ALB[AWS Application Load Balancer]
    
    subgraph ComputePool ["Serverless Edge & Container Clusters"]
        EdgeWorkers[Deno Edge Workers: Lightweight API Routing]
        GPUWorkers[EKS GPU Cluster: Heavy Video Frame FFT Analysis]
    end

    subgraph CachingLayer ["Multi-Tier Cache"]
        RedisCluster[(Redis Cluster: SHA-256 Semantic Cache)]
    end

    subgraph StorageLayer ["Durable Custody & Database"]
        PgPrimary[(PostgreSQL Primary: Write Master)]
        PgReplica[(PostgreSQL Read Replicas)]
        S3Storage[(AWS S3 Object Lock: WORM Compliance)]
    end

    ALB --> EdgeWorkers
    EdgeWorkers --> RedisCluster
    EdgeWorkers --> GPUWorkers
    EdgeWorkers --> PgPrimary
    PgPrimary -.-> PgReplica
    GPUWorkers --> S3Storage
```

* **Requirements**: 100,000 DAU, 1M scans/day, 46 peak RPS, <1.5s latency, 99.9% uptime.
* **Architecture**:
  - Stateless frontend served via Cloudflare Anycast CDN edge.
  - Multi-tier cache: Redis keyed by SHA-256 hash absorbs 40% of repeat media checks.
  - Heavy video tasks queued to an Amazon EKS cluster with autoscaling GPU nodes.
  - PostgreSQL partitioned by month with active read replicas for analytics queries.

## 2. Design the Forensic Alert Notification System

```mermaid
flowchart LR
    Event[Critical Tampering / Deepfake Detected] --> IngestTopic[SNS / Kafka Topic: alerts.critical]
    IngestTopic --> FilterWorker[Notification Routing Worker]
    
    FilterWorker --> Slack[Slack / Discord Webhooks]
    FilterWorker --> Email[SES / SendGrid Incident Dossier]
    FilterWorker --> PagerDuty[PagerDuty / Opsgenie Critical Paging]
    FilterWorker --> SSEStream[In-Browser Server-Sent Events Alert]
```

* **Requirements**: Deliver critical camera occlusion or deepfake impersonation alerts to SOC teams within 3 seconds across Slack, Email, and in-browser dashboards.
* **Architecture**:
  - Event-driven publisher pushes alert payload to an AWS SNS topic or Redis channel.
  - Decoupled worker handles rate limiting and deduplication (collapsing 50 identical alerts within 1 minute into a single incident summary).
  - Pushes real-time alerts to the browser using Server-Sent Events (SSE).

## 3. Design the Evidence File Upload & Custody System

```mermaid
sequenceDiagram
    autonumber
    actor Analyst as Forensic Officer
    participant Browser as Client Browser
    participant API as Upload Auth Gateway
    participant S3 as AWS S3 (WORM Storage)
    participant DB as PostgreSQL Custody Table

    Analyst->>Browser: Selects 500MB Surveillance Video
    Browser->>Browser: Compute SHA-256 Hash via Web Crypto (Client)
    Browser->>API: POST /evidence/presign { fileName, hash, size }
    API->>DB: Check if hash already exists (Deduplication)
    API-->>Browser: Return S3 Pre-Signed Multipart Upload URL
    Browser->>S3: PUT /video (Direct Multipart Upload, Bypassing API Server)
    S3-->>Browser: 200 OK (ETag Verified)
    Browser->>API: POST /evidence/commit { uploadId, hash }
    API->>DB: INSERT INTO custody_log (hash, s3_uri, timestamp)
    API-->>Browser: Asset Sealed & Verified
```

* **Requirements**: Ingest multi-gigabyte video evidence securely, guarantee tamper-evident integrity, and prevent API server memory exhaustion.
* **Architecture**:
  - Pre-signed direct S3 uploads bypass the API gateway completely.
  - Client computes SHA-256 hash before uploading.
  - S3 Object Lock enforces regulatory WORM (Write Once, Read Many) compliance.
